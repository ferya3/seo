# infra/db

اسکیمای دیتابیس، و چیزی که اعمالش می‌کند.

```bash
DATABASE_URL=postgresql://seo@127.0.0.1:5432/seo infra/db/migrate.sh
```

`migrate.sh` هر فایلی را که هنوز اعمال نشده اجرا می‌کند و بس. دلیلش این است که
فایل‌های مهاجرت **idempotent نیستند** — `CREATE TABLE` می‌زنند، پس اجرای دوم یک
حلقه‌ی ساده‌ی `for f in *.sql; do psql -f $f; done` شکست می‌خورد، و پشته‌ای که
نمی‌شود دوباره بالا آورد پشته نیست.

جدول `schema_migrations` می‌گوید چه چیزی اعمال شده، و **هر فایل با ردیف خودش در
یک تراکنش** اجرا می‌شود: فایلی که وسطش خطا بدهد نه جدول‌هایش می‌ماند نه این ادعا
که اجرا شده.

## چرا نه `/docker-entrypoint-initdb.d`

ایمیج Postgres آن پوشه را **یک بار** اجرا می‌کند، روی boot اول یک volume خالی، و
هیچ‌جا ثبت نمی‌کند که چه چیزی اجرا شده. یعنی مهاجرت چهاردهم هرگز به پشته‌ای که
قبلاً بالا آمده نمی‌رسد. بدتر: اگر هر دو مکانیزم با هم باشند، `migrate` یک
`schema_migrations` خالی در برابر یک اسکیمای کامل می‌بیند و روی اولین
`CREATE TABLE` می‌شکند. این دو با هم جمع نمی‌شوند؛ یکی‌شان باید باشد و آن یکی
همانی است که می‌شود دوباره اجرا کرد.

## دیتابیسی که قبلاً دستی مهاجرت شده

هر دیتابیسی که پیش از وجود این اسکریپت ساخته شده — از جمله همان چیزی که
دستورالعمل قبلی README می‌ساخت — کل اسکیما را دارد و دفترش خالی است. اسکریپت
در این حالت **متوقف می‌شود** و می‌گوید چه کار کنید، چون نمی‌تواند حدس بزند
اجرای دستی کدام فایل‌ها را اعمال کرده:

```bash
MIGRATE_BASELINE=1 DATABASE_URL=... infra/db/migrate.sh
```

این همه‌ی فایل‌های فعلی را «اعمال‌شده» ثبت می‌کند و **هیچ‌کدام را اجرا نمی‌کند**
— تنها کاری که وقتی اسکیما از قبل هست درست است.

این حالت فقط وقتی فعال می‌شود که جدول‌ها باشند و دفتر خالی باشد. روی یک دیتابیس
خالی همین متغیر هیچ اثری ندارد و هر سیزده مهاجرت عادی اجرا می‌شوند، تا کسی
نتواند با یک متغیر محیطی به‌اشتباه از ساخت اسکیما رد شود.
