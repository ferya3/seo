# orchestrator

گردش‌کار چندمرحله‌ای: برنامه‌ریزی، اعزام مرحله، انتظار رویداد، مرحله‌ی بعد.

```bash
python -m agents.orchestrator.worker            # ورکر باس
python -m agents.orchestrator.scheduler         # تیک زمان‌بندی
uvicorn agents.orchestrator.api:app --port 8200 # API
```

| فایل | کارش |
| --- | --- |
| `planner.py` | از هدف، مرحله‌ها را می‌سازد (تابع خالص) — از جمله یک مرحله به ازای هر رقیب |
| `engine.py` | ماشین حالت؛ زیر قفل ردیف گردش‌کار تصمیم می‌گیرد |
| `store.py` | وضعیت در Postgres + استیج رویداد در outbox |
| `summary.py` | خلاصه‌ی اجرایی گزارش — لایه‌ی قانون‌محور و لایه‌ی مدل |
| `trends.py` | چه چیزی نسبت به اجرای قبلی عوض شده (تابع خالص) |
| `schedules.py` | «هر دوشنبه ساعت ۹» یعنی چه، و شلیک آنچه سررسیده |
| `scheduler.py` | یک حلقه‌ی ساده: سررسیده‌ها را شلیک کن، بخواب |
| `worker.py` | مصرف‌کننده‌ی رویدادها |
| `api.py` | ساخت و خواندن گردش‌کار |

خلاصه‌ی گزارش دو لایه دارد: لایه‌ی قانون‌محور همیشه نوشته می‌شود (تابع خالص،
داخل همان تراکنش پایانی)، و لایه‌ی مدل بعد از آن و بیرون از قفل جایش را
می‌گیرد — فقط اگر `ANTHROPIC_API_KEY` ست باشد و مدل جواب بدهد. بدون کلید، هیچ
چیزی از کار نمی‌افتد.

زمان‌بندی سه تصمیم دارد که راحت غلط از آب درمی‌آیند: **ساعت ۹ در کدام
منطقه‌ی زمانی** (ذخیره و محاسبه در همان منطقه، وگرنه با تغییر ساعت یک ساعت
جابه‌جا می‌شود)، **۳۱ در ماه ۳۰روزه** (به آخر ماه چسبانده می‌شود، نه رد شدن از
آن ماه)، و **ماشینی که یک هفته خاموش بوده** (یک اجرا، نه هفت تا). هر سه تابع
خالص‌اند و بدون ساعت تست می‌شوند.

شلیک و جابه‌جا کردن `next_run_at` در **یک تراکنش** انجام می‌شود و ردیف با
`FOR UPDATE SKIP LOCKED` گرفته می‌شود — همان الگوی رله. برای همین می‌شود دو
scheduler را همزمان اجرا کرد.

رقبا **یک مرحله به ازای هر سایت** می‌گیرند، نه یک مرحله که به چند کار باز
می‌شود. ماشین حالت از قبل بلد است یک مرحله را اعزام کند و منتظر رویدادش بماند؛
مرحله‌ای که N کار تولید کند به نوع دومی از انتظار نیاز داشت — با قفل خودش،
قاعده‌ی شکست جزئی خودش و باگ‌های خودش. پشت سر هم بودنش هم برای سایتی که خزیده
می‌شود مؤدبانه‌تر است.

**خزش رقیب اگر شکست بخورد، ممیزی شما شکست نمی‌خورد.** سایت رقیب که پایین باشد
چیزی درباره‌ی سایت شما نمی‌گوید. خود مرحله در گزارش `failed` می‌ماند؛ گردش‌کار
نه. اگر هیچ رقیبی بالا نیاید، مرحله‌ی مقایسه `skipped` می‌شود.

**روند** چیزی است که زمان‌بندی را از «انبار گزارش» به «سری» تبدیل می‌کند:
گزارشی که هر هفته همان عددهای مطلق را تکرار کند به سؤالی جواب می‌دهد که
خواننده از قبل جوابش را دارد. چهار قاعده‌اش همه از یک جنس‌اند — چیزی که
درست‌به‌نظر می‌رسد ولی غلط است: **علامت جهت نیست** (بالا رفتن امتیاز خوب است و
بالا رفتن تعداد ایراد بد)، **نبودن صفر نیست** (مرحله‌ای که هفته‌ی قبل اجرا نشده
یعنی مقایسه‌ای در کار نیست، نه «از صفر به پنج»)، **جابه‌جایی کوچک خبر نیست**، و
**خزش با اندازه‌ی متفاوت نمونه‌ی متفاوت است** (سنجه‌های شمارشی کنار گذاشته
می‌شوند و همین در گزارش نوشته می‌شود).

امتیاز دسته‌ها هم مقایسه می‌شوند، و دلیلش یک اجرای واقعی بود: سایتی که روی
هر صفحه توضیح متا گرفت و طول محتوایش سه برابر شد «تغییر معناداری نیست» گرفت،
چون امتیاز کلی و تعداد ایراد اتفاقاً همان‌جا ماندند — در حالی که امتیاز محتوا
از ۶۸ به ۷۶ رفته بود.

جزئیات تصمیم‌ها در `ARCHITECTURE.md`.
